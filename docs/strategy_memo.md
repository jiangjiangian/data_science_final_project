## 1. Executive Summary (≤ 200 words)

Phase A is a **wiring test, not a result**. We built four R artefacts:
`scripts/00_synthetic_smoke.R` (synthetic CSV generator that mirrors the
data-collector hand-off schema *including* the new team-strength
columns from charter amendment #1); `R/elo_pythag.R` (pure Elo /
Pythagenpat / rest-days functions, K=4 MoV-adjusted, HFA = +24);
`R/build_recipes.R` (seven `tidymodels` recipes m1–m7 matching the
*revised* ablation order: m2 = team-strength, m3 = stadium, m4 =
weather, m5–m7 stacked); and `scripts/03a_phase_a_poc.R`, the
entry-point POC that runs the full pipeline with `initial_time_split`
and reports ROC-AUC, PR-AUC, Brier, accuracy, F1. None of the scores
this POC produces should be discussed as "results" — they are
generated from synthetic data whose signal we **defined** in
`00_synthetic_smoke.R`. The pipeline's *purpose* is to fail visibly
before real data lands. We have five strategic decisions blocking
Phase B that need main-agent input — see §5.

## 2. Why Phase A is a POC, Not a Result

### What this POC CAN demonstrate

| Claim | Evidence |
|---|---|
| Data-collector schema can flow through `recipes` end-to-end | `03a_phase_a_poc.R` reads CSV, joins team-strength, recipes prep, fits, scores |
| `compute_elo()` / `compute_pythagenpat()` / `compute_rest_days()` produce *no* future-leakage | Each uses `dplyr::lag()` or sequential loop with strict pre-game cache |
| `initial_time_split()` (NOT random) is wired in | Line 117 of `03a_phase_a_poc.R` |
| m1–m7 formula ordering matches charter amendment #2 | `R/build_recipes.R` §m1..m7 blocks; verified by name + recipe inspection |
| Stadium × wind_speed interaction in m7 works after one-hot | `step_interact(terms = ~ wind_speed:starts_with("stadium_"))` |
| PR-AUC is collected alongside ROC-AUC (charter amendment #5) | `yardstick::metric_set()` includes `pr_auc` |

### What this POC CANNOT demonstrate

1. **Any claim about CPBL.** Synthetic data was generated by us with
   a known DGP. The "AUC ranking" m1 < m2 < m7 is *baked in*.
2. **Whether Elo K=4 is right for CPBL.** Calibration of K against
   real CPBL win sequences requires real game data; the value 4 is a
   defensible default from baseball Elo literature, not a tuned
   parameter.
3. **Whether weather adds signal *after* team-strength.** The whole
   point of the new m2 (team-only) is to make this question *harder*
   than it was under the old charter (where m2 was stadium-only).
4. **Whether 大巨蛋 / 嘉義 / 台鋼 sub-groups have enough sample.** No
   amount of synthetic data answers a sample-size question about real
   venues / teams.
5. **Whether `rsample::initial_time_split(prop = 0.8)` carves a
   reasonable train/test boundary for 2020–2024 CPBL.** Charter §6.1
   actually says train = 2020–2022, validate = 2023, test = 2024. The
   POC currently uses a single 80/20 cut on synthetic data — Phase B
   must adopt the §6.1 three-way split.

### Failure mode of treating POC as a result

If anyone (us, Sub-Agent 5, the user) reads "POC m7 ROC-AUC = 0.78"
off the synthetic scoreboard and concludes "we'll deploy," that is
**identical to overfitting to the simulation**. The synthetic DGP
gives the home team a logit boost of 0.16 + skill diff + small wind
penalty; m6/m7 will trivially recover this and look good. Real CPBL
will be 0.1–0.2 AUC lower at best.

## 3. The "What Could Kill Us" List (ranked)

Five failure modes specific to this dataset, ranked by P(blow up)
× severity. Each is something Phase B must measure on real data
before going to Sub-Agent 5.

### F1. Elo cold-start in 2020 (HIGH × HIGH)
- **Symptom**: Every team starts at 1500 on 2020-04-11; first ~50
  games of 2020 carry near-zero discriminative power.
- **Why it matters now**: Charter §3.3 already flags 2020 as
  anomalous (COVID closed-door games). If we *additionally* feed cold
  Elo into m2/m5/m6/m7, those four models will look weak in 2020 for
  the *wrong reason*.
- **Mitigations** (pick one, decision needed from main agent):
  a. Burn-in: drop 2020-Q1 from training entirely.
  b. Seed Elo from 2019 final standings (need extra data fetch).
  c. Use Pythagenpat in lieu of Elo for the first 30 games per team.

### F2. Dome-stadium weather contamination (MEDIUM × HIGH)
- **Symptom**: 大巨蛋 (covered since 2024) gets weather values from
  the nearest outdoor station (charter §4.3 dome handling). m4/m6/m7
  will pick up spurious wind_speed/humidity correlations driven by
  Taipei micro-climate that have *zero* physical effect on the game.
- **Why it matters now**: Charter handles this via `is_dome` flag
  but `R/build_recipes.R` does NOT yet zero-out weather when
  `is_dome == TRUE`. POC explicitly punts this to Phase B (see
  `R/build_recipes.R` comment block, lines 24-27).
- **Phase B fix**: add `step_mutate_at(is_dome == TRUE, fn = ~ median(.))`
  inside m4/m6/m7 recipes.

### F3. Sample size at m7 (MEDIUM × HIGH)
- **Symptom**: m7 with stadium dummies (6) + weather (3) + team
  strength (3) + stadium×wind interactions (6) = ~18 predictors.
  On 2020–2022 train slice (~720 games) we are at p/n ≈ 0.025;
  for 大巨蛋 stratum alone (< 80 games) we are over-parameterised.
- **Why it matters now**: Charter §8 power analysis was based on
  the *old* m1–m7 (no team-strength); adding 3 team-strength
  variables shifts §8.2 sample-size from ~1080 to maybe ~1300.
- **Phase B fix**: glmnet with `mixture` tuned in [0.0, 0.7] (more
  L2 than L1, because we want shrinkage not selection); report
  effective DoF.

### F4. Stadium-team confounding (LOW × HIGH)
- **Symptom**: 6 of 7 CPBL teams have a dedicated home stadium →
  `stadium` and `home_team` are essentially the same variable.
  Charter amendment #4 acknowledges this; we already don't put
  `home_team` into the model.
- **Where this still bites**: when interpreting m3 (stadium-only)
  in Sub-Agent 5's SHAP plots, "stadium effect" cannot be cleanly
  separated from "home-team-as-home effect." This is a *causal*
  problem, not a fitting problem.
- **Mitigation**: explicit memo in Sub-Agent 5's evaluator report;
  do NOT claim "球場特性" without footnote.

### F5. Concept drift across 2020-2024 (LOW × MEDIUM)
- **Symptom**: 2024 saw 大巨蛋 opening + 台鋼 expansion + ABS
  (automated ball-strike) trial. Model trained on 2020-2023
  may calibrate poorly on 2024 test set.
- **Charter status**: §9 R2 already named; §7.3 demands stratified
  fairness eval.
- **Phase B fix**: add `season` factor (or `season × everything`
  interaction in m7) as a sensitivity check; do NOT add it to the
  main model.

## 5. Open Questions for Main Agent

These are the strategic decisions I need main-agent input on before
Phase B starts. Roughly ordered by what blocks the most downstream
work.

### Q1. Should `team_state.csv` be a data-collector deliverable, or do we recompute Elo inside model-builder every run?

- **Option A — Sub-Agent 2 owns it**: cleaner separation; Sub-Agent
  5 can audit one CSV; Elo recomputation is deterministic so we get
  the same numbers across model rebuilds.
- **Option B — Model-builder owns it**: zero coordination cost;
  charter amendment #7 doesn't have to ship; we already have
  `R/elo_pythag.R` working.
- **My recommendation**: Option A, *but* model-builder keeps
  `R/elo_pythag.R` as the canonical implementation that Sub-Agent 2
  calls. This avoids dual-source-of-truth.

### Q2. How should we handle the 2020 COVID season — drop, keep, or flag?

Charter §3.3 says "include but flag for sensitivity." Charter §9 R2
says concept-drift is a known risk. F1 above adds Elo cold-start as
a *third* reason 2020 is special.

- **Option A**: Drop 2020 entirely; train on 2021-2022, validate
  2023, test 2024 (~720 train, 240 val, 240 test).
- **Option B**: Keep 2020 but seed Elo from 2019 (requires data-
  collector to fetch one more season).
- **Option C**: Keep 2020 with cold Elo + flag; let m1-m7 show
  whether the noise drowns out the signal.

This blocks H1 above and is mentioned in your "Issues still under
discussion" item #4.

### Q3. The seven-inning / 雨延 / 颱風 rule from your issue #3 — do we treat all "completed" games equally, or weight by inning?

Your prompt flagged this as still-discussed. The current POC uses
`is_completed == TRUE` as a binary filter (synthetic always TRUE).
But a 7-inning rain-shortened win is *not* the same signal as a
9-inning win — variance of `home_score - away_score` is roughly
sqrt(7/9) higher in shorter games.

- **Phase A impact**: zero (synthetic).
- **Phase B impact**: if we weight by inning, MoV-adjusted Elo in
  `R/elo_pythag.R` already self-corrects somewhat (smaller diff →
  smaller K-update). The question is whether m1-m7 should add an
  `n_innings` covariate or just drop sub-9-inning games.
- **My recommendation**: drop sub-7-inning games (truly weather-
  curtailed); keep 7+ inning games unchanged.

### Q4. PR-AUC sub-group reporting — what's the threshold for "this stratum is too small"?

Charter amendment #5 added PR-AUC as a sub-group sanity check, and
F4 above flags stadium-team confounding for SHAP interpretation.

Concretely: for 大巨蛋 (probably 30-80 games over 2020-2024) and
台鋼 (only 2024 onward), do we:

- (a) Report PR-AUC with explicit "n < 50 — high variance" tag?
- (b) Refuse to report when n < 30?
- (c) Bootstrap a confidence band and only report if the band
  excludes 0.5?

This blocks H5 above.

### Q5. Are we OK with the *order* of m2–m6 as I've set it, or do you want a different priority?

The new ablation (charter amendment #2) is:
- m1 = intercept
- m2 = **team-strength** only (Elo, Pythag, rest)
- m3 = stadium only
- m4 = weather only
- m5 = team + stadium
- m6 = team + weather
- m7 = team + stadium + weather (+ interaction)

The choice of "m2 = team" sets the **must-beat** bar via amendment
#3 (m7 must beat the *upper 95% bootstrap CI of m2*, not m1).
This is a *high* bar because Elo + Pythag is genuinely strong.

Three alternatives if you think the bar is too high:
- **Alt A**: keep amendment #3 as-is. Honest, hard, possibly causes
  Bar #1 to fail on Phase B; we live with that.
- **Alt B**: relax to "m7 beats *point estimate* of m2" (no
  bootstrap CI). Less rigorous but more likely to clear.
- **Alt C**: split into two bars: "soft must-beat = m7 > m2 point
  estimate" and "hard must-beat = m7 CI excludes m2 CI." Then we
  report which we hit.

My recommendation: **Alt A**. The user picked Elo as the null
explicitly because it's the de-facto sports analytics baseline; if
weather adds nothing on top of it, *that itself is a result worth
reporting*. Failing Bar #1 is not the same as failing the project.

### 8.3 Minor code observations (no action required this round)

These were caught in code review but are *not* worth a refinement loop:

1. `R/elo_pythag.R::compute_pythagenpat()` rolling-window math is `window - 1` not `window` (off-by-one between `rs_lag` and `lag(cumsum, n=window)`). At window=30 this means we use the last 29 games not 30 — negligible practical impact. Fix in Phase B when window is itself tuned.
